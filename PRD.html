Track: Trust, but check (verify)

Every claim, stamped with the trust of its source.

A chat research assistant that rates its sources in the open Ampel system — green, orange, red — shows you exactly which claims lean on which quality of source, and lets you re-rate a source on the spot.

VERDICT72%VERIFIED
01

Problem

AI research tools hand back a finished-looking report. The reader can't tell, without re-reading and re-checking every line, which claims rest on a solid source and which rest on a vendor blog or a press release. Trustifier makes that visible at a glance, and makes it correctable: if you — or a domain expert — know a source is better or worse than the system thinks, you fix it right there, and the report reflects it immediately.

Target user (this demo): a general knowledge worker researching a topic who needs to defend the result to someone else — the "sign off without re-reading everything" test from the brief.

02

User flow

  1. Ask — user states a research topic in chat.
  2. Clarify — Trustifier asks 1–2 scripted clarifying questions to narrow angle and scope. Answers actually change which claims and sources get used.
  3. Research — a report renders as a sequence of claims, each carrying an inline trust stamp.
  4. See at a glance — a trust ledger rail on the report's edge shows one mark per source in reading order; a header verdict stamp shows the aggregate score.
  5. Check a source — click any stamp to open a source drawer: publisher, date, the heuristic's score and its reasons, and the current rating.
  6. Re-rate — set a new band with an optional reason. The stamp, the rail mark, and the header verdict update immediately.
  7. Persistence proof — refresh the page. The re-rating is still there.
03

Functional requirements

  • Exactly three trust bands — green / orange / red — each coded by color and shape, not color alone, plus a text label in the drawer and on hover.
  • Every claim links to exactly one source; every source has exactly one effective rating at a time (latest override, else the heuristic).
  • Heuristic scoring is rule-based and explainable — every score ships with a list of reasons. Not a black box.
  • Re-rating is an append-only history, not an overwrite.
  • Re-ratings persist server-side and survive a page refresh.
  • Verdict formula, fixed: % of claims whose source's effective rating is not red.
04

Design direction

The brief already specifies the signal system — green / orange / red, Ampel-style. The design work is in how that mark is drawn and how the report is laid out, not in replacing the three-band idea.

Signature element — the provenance stamp

Each band renders as a hand-stamped ink mark, not a flat dot: a rough, slightly rotated edge, and its own shape as well as its own ink color, so the signal survives without color.

05

What's real vs. stubbed

Say this out loud in the pitch — per the brief, honesty about the tape is the useful part, not a confession.

Real

  • Rule-based heuristic scorer with explainable reasons, over a hand-authored demo dataset (2–3 topics, sources spanning all three bands, one conflict-of-interest example).
  • Clarifying-question answers genuinely filter/order which claims appear.
  • Re-rating flow, live propagation to stamp/rail/verdict, and server-side persistence.

Stubbed

  • No live web research or live LLM report generation — content is hand-authored per topic and branch.
  • No real auth — a free-text "acting as" field stands in for multiple experts.
  • Storage is a JSON file, not a database.

Contract — so two people can build in parallel

Data shapes

Source { id, title, domain, domainTier, publisher, type,
        publishedDate, fundedBy?, url, heuristic:{score,band,reasons[]} }

RatingOverride { id, sourceId, band, actor, reason?, timestamp }
  — append-only; effective rating = latest override, else heuristic.band

Claim  { id, reportId, order, text, kind, sourceId }
Report { id, topicId, answers, claimIds[], createdAt }
Topic  { id, title, clarifyingQuestions:[{id,prompt,options?}] }

Endpoints

GET /api/topics POST /api/reports { topicId, answers } GET /api/sources/:id/ratings POST /api/sources/:id/ratings { band, actor, reason }

Ownership split

Person A — Frontend / UX

  • Vite + React shell, chat panel, scripted clarify flow
  • Report view, stamps, ledger rail
  • Source drawer, re-rate control, restamp animation

Person B — Backend / Data

  • Express + JSON-file store, the four endpoints
  • Heuristic scorer (domain tier, recency, sourcing type, conflict of interest)
  • Hand-authored demo topics/sources/claims content

First 20 minutes, together: lock these shapes and endpoint signatures, stub a demo.json, wire the Vite dev-server proxy — then split and build in true isolation.
